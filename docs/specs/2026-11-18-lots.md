## Goal

Users think in lots, then suppliers, not in a catalog tree. The change replaces the category → subcategory → product → budget line tree with one categorizer, the **lot**, and organizes each lot visually as Lot → Fournisseur → devis / factures.

- Lots are one global list of 25 defaults (00–24). Admins rename and reorder them. Each project can hide lots and add its own lots. *Project-lot creation removed by `docs/specs/2026-11-19-remove-project-lot-creation.md`: existing project lots are legacy.*
- Quotes, invoices, statuses, VAT/TTC rules, documents and R2 storage stay as they are.
- Production data (live since 2026-07) is migrated, not discarded.
- Suppliers also get an optional RNE number field (added at approval).

## Out of scope

- Dropping the old catalog, template, template-item and budget line tables. They stay, unused, until a later cleanup migration. The `diy_estimate` enum value also stays in PostgreSQL until then.
- Allocating one transaction across lots. One lot per transaction.
- A database link between an invoice and a quote. Only the prefill button exists.
- Adding or deleting global lots. *Extended by `docs/specs/2026-11-19-global-lots-crud.md`: an admin now adds and deletes global lots.* Reordering or renaming lots by non-admins, including project lots (a mistyped project lot is hidden and re-added). *Project-lot creation removed by `docs/specs/2026-11-19-remove-project-lot-creation.md`: existing project lots are legacy.*
- Admin access to other users' projects. The admin lot screen shows global lots only.
- Grouping the Fournisseurs page by lot.
- Any change to documents, R2 keys or R2 files.
- Any change to VAT/TTC validation or to quote and invoice statuses, types and payment methods.
- Rehearsal tooling inside the dev agent's work (see criterion 28).
- Format validation of the RNE number, deriving it from the SIRET, and an RNE column in the accounting CSV.
- The 6 views of the `analytics` schema (`backend/analytics/sql/`), the repo-root `analytics/` copy and the Power BI model: left untouched. Reworking or dropping them, and dropping the `is_selected_budget` column they read, belong to the later cleanup migration.
- The catalog and template dev seeds (`seed_catalog.py`, `seed_template.py`): left untouched (criterion 33).

## Acceptance criteria

**Global lots**
1. A global `lots` list is created by the migration with the 25 default lots of Appendix A, in that order, code stored as text ("00" stays "00"). `POST /projects` inserts no lots. A new project sees all global lots. A test asserts the 25 codes and designations and that creating a project adds no lot rows. *Extended by `docs/specs/2026-11-19-global-lots-crud.md`: the 25 defaults are the starting list, which an admin can add to and delete from.*
2. Only an admin (`is_admin`) can rename (code and designation) and reorder global lots. A non-admin gets 403 from these endpoints. Global lot code and designation are each unique among global lots (409, stable code). Lot codes are at most 10 characters and designations at most 120, trimmed, for global and project lots alike. There is no endpoint to add or delete a global lot. A rename or reorder is visible in every project immediately. The admin rename does not look at project lots: if an admin re-codes a global lot to a code a project lot already uses, that project shows both lots with the same code (accepted; they remain separate lots). *Extended by `docs/specs/2026-11-19-global-lots-crud.md`: admins also add and delete global lots (`POST /admin/lots/`, `DELETE /admin/lots/{id}`).*
3. Admin screen: a page in Paramètres next to user management (the existing admin users page), visible only to admins. It lists the global lots, with inline rename and move up/down. Non-admins do not see the entry and get 403 from the endpoints. (Layout is a human visual check; visibility and 403 are testable.) *Extended by `docs/specs/2026-11-19-global-lots-crud.md`: the screen also adds and deletes global lots.*

**Project lots and visibility**
4. A user can hide and unhide a global lot in their own project. Visibility is stored per project. Another user's project gives 404.
5. A user can add a project-only lot (code and designation typed at creation). At creation its code must differ from every global lot code and from the project's other lots (409, stable code). Users cannot rename or reorder any lot. Project lots are listed after the global lots, ordered by code. *Creation removed by `docs/specs/2026-11-19-remove-project-lot-creation.md`: no endpoint or screen adds a project lot any more; existing ones keep working.*
6. Hiding a lot that has active transactions in the project is refused (409, stable code). A lot whose transactions in the project are all soft-deleted may be hidden. Unhiding is allowed. Hidden lots are excluded from the Lots page, lot pickers, dashboard and project totals. *Project-lot creation removed by `docs/specs/2026-11-19-remove-project-lot-creation.md`; hiding and showing are unchanged, existing project lots included.*
7. A transaction's lot must be a global lot or a lot of the same project; otherwise it is refused (400/404, stable code).

**Transactions**
8. Transactions have their own required `project_id`, and every ownership check (transactions, documents, trash, exports, financial engine) goes transaction → project, not through the lot or budget line. A test covers cross-user access returning 404 for each of these.
9. Every transaction has exactly one required lot. `budget_line_id` becomes nullable and is unused by application code. The `is_selected_budget` column stays in the database, unused by application code, because the production `analytics` views read it; it is dropped by the later cleanup migration. The analytics views are not modified: they keep showing only transactions that have a budget line, i.e. those from before the change.
10. `TransactionType` is `quote` and `invoice` in the API, schemas, filters, UI and export. The API refuses `diy_estimate` (422/400 with a stable code). The value stays in the DB enum. `is_selected_budget` leaves the API and UI. The "retenir comme budget" toggle is gone.
11. Each transaction has an optional `title` (libellé, at most 255 characters) and an optional `reference` (at most 100), both free text, trimmed, an empty value stored as null. `description` stays as notes. The text search matches title and reference. When the title is empty the UI shows "Devis · {supplier}" or "Facture · {supplier}", or just "Devis" / "Facture" with no supplier.
12. A transaction may have no supplier. The existing constraints on amounts, VAT/TTC and type-specific fields still hold. `ck_transactions_selected_budget_candidate` is dropped and a new check constraint allows only `quote` and `invoice` as `transaction_type`, so the database also refuses `diy_estimate`. A test covers each remaining constraint.
13. Create/update endpoints take a lot. The product-scoped route, whole-product/breakdown logic, and all of these are removed from the API: the catalog, template, template-item and budget-line endpoints, and the project-from-template route. Onboarding uses `POST /projects`. New errors follow `docs/api/errors.md` (stable `code`, English `message`, `field`, French translation by code).
14. Prefill: each quote has "Ajouter une facture pour ce devis". It opens the invoice form with the same lot, supplier, libellé, VAT rate and amount HT, all editable. Saving creates an ordinary invoice with no link column or foreign key to the quote.

**Suppliers and lots**
15. A per-project (project, supplier, lot) assignment exists. Creating a transaction with a supplier assigns that pair if missing. Manual assignment works for suppliers with no transaction. Manual unassignment is refused (409, stable code) while the supplier has active transactions in that lot, and allowed once it has none. When a supplier's last active transaction leaves a lot, the supplier stays assigned.
16. Suppliers stay shared across a user's projects. The Fournisseurs page has a lot filter and a "Lots" badges column, with no grouping. The supplier detail page shows lot, libellé and référence instead of category/product/budget line.

**Financial engine**
17. The engine aggregates by lot. Per lot: **Devis retenus** = sum of TTC of active `validated` quotes; **Facturé** = sum of TTC of all active invoices, split paid / unpaid / on hold; **Reste à facturer** = Devis retenus − Facturé, with a negative value flagged as an overrun (dépassement). The project total is the sum over visible lots. Tests cover:
    - each quote status and each invoice status;
    - a soft-deleted transaction;
    - an empty lot;
    - a negative remainder;
    - project total = sum of lots;
    - a global lot and a project lot in the same project.

    *Superseded by `docs/specs/2026-11-19-money-model-and-screens.md` (Coût prévu, Facturé, Payé, À payer; no Reste à facturer or overrun).*
18. Facturé means all active invoices everywhere, including the dashboard's "Dépenses dans le temps" and "Répartition par fournisseur" (both paid-only today, per `financial_engine.py`). Every visible lot appears in the engine output with zero totals when empty. Soft-deleted transactions and documents never count. *Superseded by `docs/specs/2026-11-19-money-model-and-screens.md` (Coût prévu, Facturé, Payé, À payer; no Reste à facturer or overrun).*

**Pages**
19. The Budget page becomes the "Lots" page: a table of every visible lot with its totals, empty lots included with an empty state. The old tree, `ProductStructureDialog` and `DeleteBudgetLineDialog` are unreachable. Route `/lots/:lotId` shows one card per supplier plus "Sans fournisseur" (only when it has transactions). Each card has separate devis and factures lists and add-devis / add-facture actions. An empty lot shows an empty state. A lot not visible in the project gives not-found. (Layout is a human visual check; route, data and empty state are testable.) *Superseded by `docs/specs/2026-11-19-money-model-and-screens.md` (Coût prévu, Facturé, Payé, À payer; no Reste à facturer or overrun). The Lots page and the lot cards show the new figures.*
20. Onboarding has no template step. Templates appear nowhere in the user-facing app.
21. Dashboard: both category widgets switch to lots. "Budget vs dépenses réelles" becomes a bar chart of Devis retenus vs Facturé per lot, showing only lots with a non-zero amount. "Répartition par catégorie" stays a treemap and shows Facturé per lot. "Top 5 Écarts budgétaires" is computed per lot from criterion 17. "Budget à valider" and its endpoint are removed. The other widgets stay, showing lot where they showed category/product. A test checks the new payload shapes. *Superseded by `docs/specs/2026-11-19-money-model-and-screens.md` (Coût prévu, Facturé, Payé, À payer; no Reste à facturer or overrun). The dashboard is rebuilt by that spec (criteria 19–21b).*
22. The Transactions page (with a lot filter), Documents page, trash and issue-report context show lot, libellé and référence instead of category/product/budget line. Restoring a trashed transaction whose lot is hidden in its project unhides the lot. A deleted supplier follows the existing dependency-aware restore order (§6.7).
23. The accounting CSV drops Category, Subcategory, Product and Budget line. It adds "Lot code", "Lot", "Title" and "Reference". "Supplier reference" is renamed "Supplier SIRET" (it holds the SIRET today, per `export.py` `_supplier_reference`). The `diy_estimates` export filter value is removed. A test checks the header row.

**Migration and deploy**
24. One Alembic migration, with a working downgrade. It:
    - creates the lots, project-lot visibility, supplier↔lot assignment, and the new transaction columns;
    - backfills `transactions.project_id` from the budget line's project;
    - sets each transaction's lot (active and soft-deleted) from its budget line's product via the Appendix mapping;
    - sets every migrated transaction's `title` to its budget line name (no transaction has a title before the change), cut to 255 characters;
    - creates a supplier↔lot assignment for each (project, supplier, lot) pair found;
    - adds the supplier RNE number column (criterion 32);
    - leaves documents, their `transaction_id` and all R2 objects untouched;
    - leaves old tables in place.
25. Mapping is per sous-catégorie with product-level exceptions, matched on category, sous-catégorie and product names (as in `backend/app/seed/data/catalog.json`). If a product used by any transaction (active or soft-deleted) falls in a sous-catégorie absent from the Appendix, the migration stops with a message naming it, instead of guessing. A test covers the stop.
26. Existing `diy_estimate` rows become quotes. If `is_selected_budget` was true: status `validated`. Otherwise: `to_confirm`. Each gets a note appended (not overwriting) to `description` saying it was a former DIY estimate. Existing quotes with `is_selected_budget = true` become `validated`. Quotes already `validated` but not retained are not changed. The migration logs the counts of each conversion. Migration-test assertions on a populated fixture:
    - transaction count unchanged;
    - TTC sum per project of (retained quotes + former retained DIY) before = `validated` quotes after, to the cent, except for the validated-but-not-retained quotes;
    - invoice totals unchanged;
    - every document still points to the same transaction;
    - no null lot or `project_id`.
27. Migration runs upgrade → downgrade → upgrade on a populated test database, in addition to CI's `alembic upgrade head` on an empty one (`.github/workflows/backend-migrations.yml`).

Yoann reviews it.

## Risks

- **Size.** One branch covers schema, migration, engine, about 10 API areas and about 10 screens, and removes whole API surfaces. Review qa on the migration and engine first.
- **Mapping errors on real data.** A wrong mapping silently re-categorizes real family spending. Tests prove counts and sums, not correctness; the approved Appendix and the rehearsal report are the protection. Products unused by any transaction are ignored by the stop rule.
- **Dashboard figures change at deploy.**
  - Budget is now `validated` quotes only.
  - Facturé now counts all active invoices, so completion % and the spending-over-time and supplier-distribution charts rise by the unpaid and on-hold amounts.
  - Validated-but-not-retained quotes start counting.
  - These are expected; the rehearsal report shows them before deploy.
- **Ownership regression.** Lots are global, so the lot no longer proves ownership. Any query still joining through lot or budget line instead of `transactions.project_id` could leak data across users. Criterion 8 tests it.
- **Admin rename affects everyone.** Renaming or re-coding a global lot changes every project at once, and can leave a project with a global lot and a project lot sharing a code (accepted, criterion 2).
- **Rollback.** `budget_line_id` becomes nullable, so a rollback after users enter lot-based data loses those rows. The real path is restoring the pre-deploy backup (accepted). The old tables stay intact for the one release.
- **Enum.** `diy_estimate` stays in the PostgreSQL enum; the API and a check constraint refuse it. This is a dead value until the cleanup migration.
- **Analytics views go stale.** The 6 `analytics` views and the Power BI reports built on them only see transactions from before the change, until the cleanup migration reworks or drops them (accepted).
- **Breaking API.** Removing catalog, template, template-item, budget-line and from-template endpoints breaks any open tab or client on the old frontend. The auto-update reload (v1.10.0) should cover tabs; verify it triggers. Old bookmarks with `diy_estimates` return an error (accepted).
- **CSV consumers** see changed headers.
- **Public repo.** The mapping appendix and migration contain no sensitive data, since the catalog is already in `backend/app/seed/data/catalog.json`.
